# Mobile Pass — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans (superpowers:test-driven-development for pure logic, e.g. head fitting and tilt maths). Project skills that apply: `3d-model`, `tune-animation`, `create-animation`.

**Goal:** Make faizaan.tech genuinely good on phones, keeping desktop pixel-identical, plus accelerometer-driven head movement on mobile.

**The owner's report** (iPhone, portrait, light mode, viewing the full site inside a claude.ai artifact via the Orca app; screenshot in the coordinator's session):
> "Mobile is VERY messed up. The head is taking up all the space. The text is too large and the text colour is not the same. Make the sizing of everything appropriate for mobile. ALSO on mobile, the head should move based on the accelerometer if present. [Fix] anything else you might come across that needs to be fixed."

**What the screenshot shows (390-ish × 844 portrait):**
- The chrome head fills the whole width and most of the height.
- The name "(faiz)aan sakib" is so large that only fragments show behind the head, and it renders **black**.
- The Doto subtitle lines are huge and dark, colliding with the link dock.
- Glass pieces look fine; the player tab ("+ player", vertical) sits mid-right; the link dock is at the bottom.

**Root causes found so far (verify them):**
1. **Text colour:**
   - `src/styles/global.ts` is still the Vite starter template: `color-scheme: light dark`, `color: rgba(255,255,255,.87)` on `:root`, a `@media (prefers-color-scheme: light)` block, `a { color: #646cff }`, and `button:hover { border-color: #646cff }`.
   - The site's text components (`HeaderText`, `SubtitleText`, …) set no colour of their own; they inherit. Inside a host page with its own body colour, or in light mode, the text goes dark.
   - Fix: give the site an explicit, host-independent palette (white text as on desktop). Set the colour on the components, and on `html`/`body`/`#root` with a dark background. Remove the template leftovers that change the look (`color-scheme: light dark`, the light-mode block, the template link/button colours), checking each against every component that relied on them, e.g. the Player's `:hover` pinning ruling.
2. **Head size:**
   - The r3f camera is fov 75 (vertical) at z ≈ 5 (`src/components/Head/index.tsx` `CAMERA_Z` and the per-frame `cameraZ` lerp). In portrait, the horizontal field shrinks and the head overfills.
   - Fix: fit the head to the viewport's width **and** height (a pure `fitCamera(aspect, …)` → camera z or head scale, tested), targeting on phones ≈ 60–70% of the viewport width and ≤ ≈ 45% of the height, centred between the name and the link dock.
   - Desktop (≥ 1024 px wide, landscape) must produce exactly today's camera z, so a test pins it.

## Requirements
1. **Head fits on phones:** portrait and landscape, handling resize and orientation changes. Desktop is unchanged.
2. **Typography scales:**
   - The name header fits within the viewport width on phones on one line (vw-based clamp, with the header's per-letter width locking re-measuring at the new size).
   - The six subtitle lines scale down and re-space so they never collide with the link dock, the player tab or the head's face.
   - The per-letter font cycle, fitScale and shockwave still work at small sizes.
3. **Colour is host-independent:** white text (and the site's intended colours everywhere) in light mode, dark mode, and inside a host page whose body sets `color: #111; background: #fafafa`. Test by emulating `prefers-color-scheme: light` **and** by wrapping the built page in such a body.
4. **Accelerometer head movement:**
   - On touch devices, when device-orientation data is present, the head's yaw and pitch follow the phone's tilt. Tilt is measured relative to the attitude when the visitor entered (calibrate on enter, and re-calibrate on orientation change), smoothed, and clamped to the same ranges as the desktop mouse-follow (`MOUSE_YAW` 22° yaw, `MOUSE_PITCH` 10° pitch).
   - Handle the screen orientation: landscape swaps and flips the axes (`screen.orientation.angle`).
   - On iOS, `DeviceOrientationEvent.requestPermission()` must be called from a user gesture: request it on the Splash "enter" tap. If it's denied or unavailable, fall back silently to today's behaviour.
   - Put the maths in a pure, tested module, e.g. `src/choreography/tilt.ts` (beta/gamma + screen angle + calibration → yaw/pitch targets). Wire it through a small hook, e.g. `useDeviceTilt`.
   - With reduced motion: no tilt-follow.
   - Note: inside an iframe (e.g. the claude.ai artifact viewer), device-orientation events may be blocked by permissions policy. That's fine; degrade gracefully and report what you observe.
5. **Mobile audit, and fix what you find.** At minimum check each of these on 393×852 @3× (iPhone 15), 375×667 @2× (iPhone SE), 412×915 @2.6× (Android), and 852×393 landscape:
   - Splash (layout, tap target, text size).
   - Glass pieces (size and count relative to the viewport; drag vs touch; frame cost on mobile).
   - The DJ pad position.
   - The player tab and drawer (the vertical "+ player" label renders as "pl ayer"; fix the letter-spacing or orientation).
   - The link dock over the subtitles.
   - Safe areas: notch and home indicator (`env(safe-area-inset-*)` on every fixed element at the edges).
   - `100vh` vs `100dvh`.
   - The canvas DPR cap on phones (e.g. ≤ 2).
   - Overflow and horizontal scroll: none.
   - Audio unlock on iOS (Web Audio needs the enter tap).
   - Grid density.
   - Performance: frame cost on a 4× CPU-throttled mobile emulation, compared before and after.

   Record every finding as fixed, or as a ruling with a reason.
